# Pacey — Design Guidelines

Design context for the Pacey running product (`pacey/` plus its APIs
under `api/`). Everything below is Pacey's own convention — do not apply
it to the personal site around it. Site-wide context lives in
[`../.impeccable.md`](../.impeccable.md), product scope in
[`PRODUCT.md`](PRODUCT.md), and voice in
[`pacey-writing-style.md`](pacey-writing-style.md).

## Users

Recreational runners aged 25–50 who want structured feedback on their running form without hiring a coach. Used at home on desktop or tablet, typically after a run session. Comfort level: can take a slow-motion video on a phone, screenshot frames, and upload them to a web tool.

## Brand Personality

Three words: **clear, measured, encouraging**. Like a thoughtful running coach who explains _why_ something matters, not just what to do. Not clinical (intimidating) and not loud gym-bro energy.

## Aesthetic Direction

Light theme — daytime health/wellness context. Clean editorial feel: generous whitespace, confident typography, restrained use of colour. The palette is navy + sky blue (already established). The site belongs to a personal projects/playground section so it should feel crafted and personal, not corporate SaaS.

## Design Principles

1. **Clarity first** — every element on screen should be immediately legible. Contrast, size and spacing serve reading, not decoration.
2. **Confident hierarchy** — primary actions (Analyse Form) must look unmistakably primary. Secondary actions should step back.
3. **Structured calm** — the analysis dashboard should feel like a thoughtful report, not a dashboard full of widgets.
4. **No ban patterns** — no side-stripe borders on cards, no gradient text, no identical card grids.
5. **Earn every element** — if something doesn't aid comprehension or navigation, remove it.

## Accessibility

- **WCAG AA compliance** is the minimum bar. All text/background combinations must meet 4.5:1 contrast for small text and 3:1 for large text and UI components.
- **Reduced motion is respected.** Users with `prefers-reduced-motion: reduce` get instant state changes — no spinners, shimmer sweeps, slide animations, or pulses. This is a quality-floor requirement, not an enhancement.
- **Keyboard navigation works everywhere.** Every interactive element has a visible `:focus-visible` outline (using `--pacey-blue` at 0.125rem). Focus is never removed without replacement.
- **ARIA on all overlays.** Modals, popups, and bottom sheets use `role="dialog"`, `aria-modal="true"`, and `aria-label`. Focus is trapped while open and returned to the trigger on close.
- **Color is never the sole information channel.** Run-type tags, calendar dots, and chart data are reinforced with text labels or tooltips, not colour alone.

## Motion Philosophy

- **Motion answers user action.** Opening, expanding, confirming, switching tabs — these transitions show what changed and are welcome.
- **Non-user-triggered motion is rare and deliberate.** A single orchestrated moment (one page-load reveal or one skeleton-to-content crossfade) lands better than scattered fade-and-slide entrances on every card.
- **Durations are short.** UI feedback transitions are 0.15–0.3s. Loading loops (shimmer, halo) are 1.5–2.5s. Nothing animates for longer than it takes to perceive.
- **Easing is consistent.** `ease` for simple state changes, `cubic-bezier(0.4, 0, 0.2, 1)` for material-style transitions, `cubic-bezier(0.32, 0.72, 0, 1)` for sheet slides. No spring physics unless the motion is explicitly playful.

## Dark Mode

- **Dark mode is a first-class theme, not an afterthought.** Every colour token has a dark counterpart. Surfaces, borders, shadows, and accents all flip coherently.
- **Contrast must pass in both themes.** A colour that passes AA in light mode must also pass in dark mode. When a token lightens in dark mode (e.g. `--pacey-blue` goes from `#457b9d` to `#6ba3d0`), text on it must darken accordingly (use `--pacey-btn-primary-text` pattern).
- **Theme is toggle-driven** via `data-theme` attribute on `<html>`. The toggle is accessible in both the sidebar (desktop) and settings popup (mobile).

## Spacing

- **Spacing should be tokenized.** A shared scale (`--pacey-space-xs` through `--pacey-space-xl`) prevents every component from inventing its own padding/margin values and maintains vertical rhythm.
- **Generous whitespace is a feature, not wasted space.** The brief calls for an editorial feel — content should breathe. Avoid cramming multiple sections into a single viewport on desktop.
- **`clamp()` for responsive spacing.** Key spacing values should scale smoothly with viewport width rather than jumping at breakpoints.

## Loading and Empty States

- **Skeletons over spinners where possible.** Shimmer skeletons that approximate the final layout shape reduce perceived wait time better than generic spinners.
- **Empty states are invitations to act, not blank screens.** When there's no data, show a brief explanation and a clear next step (e.g. "Connect Garmin to see your training history").
- **Errors explain what happened and how to fix it.** Error messages are specific and actionable, never vague or apologetic. They use the interface's voice, not a person's.

## Colour System

- **All colours flow through CSS custom properties** (`--pacey-*`). Hardcoded hex values in component styles are a bug — they break dark mode and make the palette impossible to maintain.
- **Semantic colour tokens** map to the palette: `--pacey-accent-green` (success/scheduled), `--pacey-accent-amber` (caution/gaps), `--pacey-accent-red` (error/danger). These are used consistently across the app.
- **Run-type tag colours** are the one exception to full tokenization — they represent categorical data (Easy, Tempo, Speedwork, etc.) and may use distinct hues, but should still be defined as tokens for dark-mode coherence.

## Button Width

- **Contextual actions hug their content.** A button that acts on a card, list row or note (expand, retry, "use this", explore) sizes to its label — `.pacey-btn-inline` is the shared compact class for that — and never stretches edge to edge inside its container.
- **Full width is deliberate, not default.** `.pacey-btn` keeps `width: 100%` because form submits and stacked mobile action rows want it; anything else opting out is a design choice made with `.pacey-btn-inline` or a scoped override, not an accident of the base rule.
- **Icon controls are fixed touch targets.** Dismiss and close icons keep at least a 44px square target, muted ink, and the visible focus outline — `aria-label` carries the accessible name, no visible text required.

## Disclosure Animation

- **One shell for every expanding panel.** `.pacey-disclosure` is a single-row grid that animates `grid-template-rows` `0fr → 1fr` via its `.is-open` class — the panel opens to the content's own height, so there is never a guessed `max-height`, a JS pixel measurement, or a timer delay.
- **The clipped inner only clips.** `.pacey-disclosure-inner` carries `min-height: 0`, `overflow: hidden`, and an opacity `0 → 1` fade — nothing else. Padding, borders and gaps belong on a semantic descendant inside it, because a padded or bordered direct grid child keeps a visible floor while collapsed; the outer wrapper keeps none either.
- **Timing is fixed.** Rows transition `0.28s cubic-bezier(0.4, 0, 0.2, 1)`, the inner opacity `0.2s`. Under `prefers-reduced-motion` all disclosure and chevron transitions drop to `none` — the state still changes, instantly.
- **Never `[hidden]` on an animated wrapper.** `display: none` kills the transition. A closed panel is `inert` + `aria-hidden="true"` instead, so collapsed content leaves the tab order and the accessibility tree. The trigger's `aria-expanded` stays the authoritative announced state, and every panel goes through the shared `setDisclosureExpanded(panel, open, trigger)` helper so class, inert and ARIA can never drift — collapsing returns focus to the trigger first.

## Elevation

- **Static vs interactive depth.** Passive paper sheets — containers the runner can never pick up, like the content header, no-goal note, goal suggestions, race recap, chart cards, insights and the plan's status card — carry the shallow `--pinboard-shadow-static` and never gain elevation on hover. Surfaces that can be acted on (metric tiles, activity rows, pillar cards, workout slips) keep `--pinboard-shadow` at rest and lift to `--pinboard-shadow-hover`.
- **Depth is the only difference between sheets.** The static override changes shadow alone — the paper grain, tape, pushpins, tilt and the inset top-edge highlight are shared and stay identical, so passive containers still read as the same pinned paper, just lying flatter.
- **Nested controls stay interactive independently.** A button, link or disclosure trigger inside a passive sheet keeps its own hover and focus feedback — the sheet around it being static does not flatten what sits on it.

## Goal Dialog vs Onboarding

- **Two goal flows, kept apart.** The multi-step onboarding screens exist only for a first-run account that has never chosen a goal. Every in-app goal action — set a goal, replace one, use a suggestion, edit the live one — opens the single-step goal dialog (`openEditGoalPopup` with `mode`/`suggestion`/`trigger`) over the dashboard instead.
- **Modes decide the frame, not the form.** `edit` pre-fills the live goal ("Edit race goal" / "Save changes" and the opt-out); `create` and `replace` open blank race fields with the account's own profile values carried over ("Set a race goal" / "Set goal", no opt-out). A suggestion supplies only type and target time — race name and date are always the runner's own.
- **Nothing is destroyed by opening it.** Replacing a goal keeps the old goal, course and caches in place until the submit saves; the plan-change warning lives on the save path, and backing out loses nothing.
